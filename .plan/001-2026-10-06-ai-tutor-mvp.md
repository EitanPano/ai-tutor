## Goal

Ship an authenticated web app where a developer can:

1. **Ask** a coding question (prose + code blocks) inside a thread.
2. **Get an AI explanation** streamed back, with follow-ups that keep the thread's context.
3. **Get step-by-step guidance**: turn a thread into a guide whose steps they work through and check off.
4. **Generate a quiz** (multiple choice) from a thread or a topic, take it, and get it graded.
5. **Track progress** per topic over time.

Done means every acceptance criterion in `Validation` (AC01–AC12) passes, run against a real
Postgres and a deterministic fake AI provider, plus one manual smoke run against the real Claude API.

### Out of scope (MVP)

- Running user code. That needs a sandbox and is its own security project.
- Free-text quiz answers graded by AI. The MVP is multiple choice only, so grading is deterministic.
- Password reset and email verification, because both need an email provider (Q3).
- Teams and classrooms. There is no `org` table; all data is owned by a user (Q2).
- Payments, admin console, i18n, mobile app, and a self-serve account export/delete UI. The data model already supports soft delete.
- Spaced repetition and adaptive difficulty.

### Target architecture

```
Browser ──► frontend/  Next.js 16 (App Router, client-side data fetching)
   │
   └── fetch, credentials: include ──► backend/  Express 5 API ──► Postgres 18
                                          │
                                          └──► Anthropic Messages API (server-side only)
```

- There are two apps: the frontend on `localhost:3000` and the API on `localhost:4000`. There is no hosted
  environment (Q11). Both are on the same site, so a `SameSite=Lax` cookie works across them, and CORS only allows
  `FRONTEND_URL` with credentials (this rule comes from `.claude/agents/backend.md`).
- The Anthropic key exists only in the backend environment. The browser never calls Anthropic.
- The backend has three layers. `backend/src/route/` handles HTTP and Zod validation.
  `backend/src/service/` holds the domain rules and enforces ownership, scoping every query to the signed-in user
  (files like `thread.service.ts`).
  `backend/src/lib/` holds the db, the tutor provider and rate limiting.
- The frontend uses client components with TanStack Query and a typed client in `frontend/src/lib/api/`.
  `frontend/src/proxy.ts` (Next 16's renamed middleware) only redirects to `/login` when the session cookie is missing.
  It's a UX convenience; the backend is the only authority on auth.

### Domain model (Postgres)

These terms go into `.doc/glossary.md` in P0 before they're used anywhere else:

| Term | Meaning |
|---|---|
| `user` | An account. The table is `app_user` because `user` is a reserved word in Postgres. |
| `session` | An **auth** session only. It never means "study session". |
| `topic` | A subject from the fixed taxonomy (`react`, `sql`, `git`, …, `other`). |
| `thread` | A conversation made of questions and explanations. |
| `message` | One turn in a thread (`role`: `user` / `assistant`). |
| `guide` | Step-by-step guidance generated from a thread. |
| `step` | One ordered item in a guide (table `guide_step`). |
| `quiz` | A generated set of multiple-choice items. |
| `quiz_item` | One question in a quiz. It's not called "question", because that word means the user's coding question. |
| `attempt` | One graded submission of a quiz (table `quiz_attempt`). |
| `ai_call` | Ledger row for each model call: model, tokens, cache reads, stop reason, latency. |

Table conventions:

- Every `id` is `text` (UUIDv7) and every table has a `created_at timestamptz` column.
- User-deletable rows get a `deleted_at` column.
- Every tenant table has `user_id NOT NULL` (foreign key, indexed), and every query filters on it (Q2).

| Table | Key columns |
|---|---|
| `app_user` | `email citext UNIQUE`, `password_hash` (argon2id), `display_name`, `time_zone` (IANA) |
| `session` | `token_hash` (SHA-256 of a 256-bit random token), `user_id`, `expires_at` |
| `topic` | `id` (slug), `name`. Seeded. |
| `thread` | `user_id`, `topic_id`, `title`, `updated_at` |
| `message` | `thread_id`, `role`, `content` (text, append-only), `status` (`complete` / `incomplete` / `failed`) |
| `guide` / `guide_step` | `thread_id`, `topic_id`, `title` / `guide_id`, `position`, `title`, `body`, `hint`, `done_at` |
| `quiz` / `quiz_item` | `thread_id` (nullable), `topic_id`, `difficulty` / `quiz_id`, `position`, `prompt`, `choice jsonb` (4), `answer_index`, `explanation` |
| `quiz_attempt` | `quiz_id`, `user_id`, `answer jsonb`, `score`, `submitted_at` |
| `ai_call` | `user_id`, `kind` (`explain` / `guide` / `quiz`), `model`, `input_token`, `output_token`, `cache_read_token`, `stop_reason`, `refusal_category`, `latency_ms` |
| `rate_limit` | Backing store for the login and API limiters. Keeping it in Postgres means no Redis for the MVP. |

- Progress is computed from SQL aggregates, not stored counters. A materialized view comes later only if P5
  measurements show a need.
- `backend/db/schema.sql` and `backend/db/migration/NNN-<name>.sql` (up and down) are the source of truth,
  per the `database-schema` skill.

### API surface

Routes are singular (naming rule). Every non-2xx response uses the error shape from the `error-handling` skill.

| Method & path | Purpose | Notes |
|---|---|---|
| `POST /api/user` | Sign up | Creates the user and the session in one transaction |
| `POST /api/session` | Log in | Rate limited to 5/min per IP + email |
| `GET /api/session` | Current user | 401 when there's no session |
| `DELETE /api/session` | Log out | |
| `GET /api/topic` | Topic taxonomy | |
| `GET` / `POST /api/thread` | List (cursor pagination) / create | Create takes a `topicId`, default `other` |
| `GET` / `PATCH` / `DELETE /api/thread/:id` | Read / rename or change topic / soft delete | |
| `POST /api/thread/:id/message` | Ask a question. **SSE** response. | 409 if a generation is already in flight or the thread is full, 429 if over budget |
| `POST /api/thread/:id/guide` | Generate a guide | Structured output |
| `GET /api/guide/:id` | Read a guide | |
| `PATCH /api/guide/:id/step/:stepId` | Mark a step done / undone | |
| `POST /api/quiz` | Generate a quiz from a `threadId` or a `topicId` + `difficulty` | |
| `GET /api/quiz/:id` | Take a quiz | **Never** returns `answer_index` or `explanation` |
| `POST /api/quiz/:id/attempt` | Submit an attempt and get the graded result | 422 unless every item is answered |
| `GET /api/progress` | Dashboard data | |
| `GET /health` / `GET /ready` | Liveness / DB reachable | |

- Accessing another user's resource returns **404, not 403**, so the response doesn't confirm the resource exists.
- SSE events, in order: `message.start` (ids), then `delta` (text), then either `message.complete` (usage) or
  `error` (standard error shape).
- The client reads the stream with `fetch` + `ReadableStream`, because `EventSource` can't send a POST.
- If the client disconnects, the backend aborts the upstream call and saves the partial answer as `incomplete`.

### AI integration

**Provider abstraction**
- The official `@anthropic-ai/sdk` lives in `backend/src/lib/tutor/`.
- The `TutorProvider` interface has two implementations. `anthropic` is the real one. `fake` is deterministic
  and is used by unit, integration and e2e tests.
- `AI_PROVIDER=fake` is the default in `backend/.env.example`, so day-to-day development costs nothing. It's set
  to `anthropic` only to see real answers (A9).
- The backend refuses to boot with `AI_PROVIDER=fake` when `NODE_ENV=production`.

**Model** (Q4)
- One env var, `AI_MODEL`, defaults to `claude-haiku-4-5` for every route.
- Requests omit `thinking`, so Haiku 4.5 runs without it. They also omit `effort`, which Haiku 4.5 rejects.
- Switching to a Sonnet or Opus 5.x model is a code change, not just a config change. Those models always think, so
  thinking blocks would have to be stored and replayed. That's out of scope (A9).
- There's no topic-classification call: the user picks the topic when starting a thread (A9).

| Route | Call | `max_tokens` |
|---|---|---|
| explain | `messages.stream`, rendered as it arrives | 2048 |
| guide | Structured output (`output_config.format`, Zod schema) | 4096 |
| quiz | Structured output | 4096 |

- An explanation that stops on `max_tokens` is saved as `incomplete`, and the UI says it was cut off.
- The UI shows a "Thinking…" state until the first text delta arrives.

**Validating output**
- Structured output is **re-validated** with the same Zod schema before anything is persisted. The checks:
  `answer_index` is 0–3, the 4 choices are distinct, and a guide has 3–8 steps.
- On invalid output the backend retries once. If that also fails, it returns 502 `ai_invalid_output`.

**Refusals** (Q5)
- Every call checks `stop_reason === "refusal"` before reading the content.
- There are no fallbacks. A refusal returns `ai_refused` with a hint to rephrase.
- A refusal mid-stream discards the partial text and saves the message as `failed`.
- `ai_call.refusal_category` records `stop_details.category`, so the refusal rate can be measured.

**Caching and history**
- The system prompt and topic list are frozen and sent first. Top-level auto `cache_control` lets
  multi-turn threads reuse the prefix.
- Haiku 4.5 only caches a prefix of at least 4,096 tokens, so short threads won't cache. `ai_call.cache_read_token`
  shows when caching happens.
- History is append-only plain text: earlier questions and answers are sent as text. Editing earlier turns would
  break the cache.
- A failed turn (the question and its `failed` answer) is left out of later requests. Retry re-sends the question.
  An `incomplete` answer is sent as it is.
- A thread holds at most 25 messages (Q6). Asking returns 409 `thread_full` when the question and its answer would go
  past 25, which allows 12 questions. History is never trimmed.

**Prompt injection**
- The model has no tools and there are no secrets in its prompt.
- Output is rendered as markdown with raw HTML disabled.
- The worst case is a bad text answer, never an action taken.

**Budget and cost** (A9)
- Each user has a daily token budget (`AI_DAILY_TOKEN_BUDGET`, default 50,000 input + output tokens), summed from
  `ai_call`. On Haiku 4.5 that caps a user at about $0.25 a day, even if every token is output.
- Each user can have at most one generation in flight.
- `AI_ENABLED=false` turns every AI route off (P6 step 3).
- The API key lives in its own Anthropic Console workspace with a low monthly spend limit, as a hard backstop
  (P0 step 11).
- Estimate: an explanation of 2k input and 800 output tokens costs about $0.005. P2 step 6 checks this with real
  calls.

## Open Questions

Write your answer on each `Answer:` line, or reply "accept recommendations". The plan is updated once answers arrive.

**Q1 — Runtime and package manager.** **Answered on 2026-10-06.**
- Package manager: Bun. `AGENTS.md`, `.claude/agents/*.md`, the `writing-tests` skill and AC01 now use
  `bun run` / `bunx`.
- Runtime: Node 24 LTS for everything, with Bun as the package manager and script runner. Playwright doesn't
  officially support Bun, and the guardrail hooks run with `node`, so Node is required either way.
- Node 26 becomes Active LTS on 2026-10-28 and reaches end of life on 2029-04-30, one year after 24. The project
  moves to 26 in P6 (step 3).
- Rejected: the Bun runtime for `backend/`. It would mean two runtimes in prod, and the SSE abort-on-disconnect path
  would rely on Bun's `node:http` compatibility.

**Q2 — Tenancy.** **Answered on 2026-10-06: no `org`. All data is owned by a user.**
- Why: no group feature is in scope (teams and classrooms are out of scope). With exactly one org per user, an
  `org_id` filter returns the same rows as `user_id`, so it would add columns and tests without adding security.
- Keeping a later `org` cheap:
  - Every tenant table has `user_id NOT NULL` with a foreign key and an index. Adding `org_id` later is then one
    backfill statement per table (`UPDATE … FROM app_user`).
  - Ownership scoping lives in one service-layer helper that takes `auth: { userId }`. Adding `orgId` later changes
    that helper, not every query.
- The `database-schema` skill lists `org` as a core table. P0 step 3 adds a note there that this product doesn't
  use it, so no agent creates one.

**Q3 — Auth method.** **Answered on 2026-10-06: email + password with server-side sessions.**
- No third-party dependency, and Playwright can test it end to end.
- Password reset is deferred, so an operator script handles resets. GitHub OAuth is the fast-follow, since it suits a
  developer audience.
- Rejected:
  - GitHub OAuth only: needs an OAuth app per environment, the e2e tests would have to stub GitHub, and users
    without a GitHub account are locked out.
  - The Better Auth library: its own `user` / `account` / `verification` tables clash with our naming.
  - A managed provider (Clerk, Auth0): adds a vendor and cost, and stores user data outside our database.

**Q4 — Model.** **Answered on 2026-10-06: `claude-haiku-4-5` on every route, with thinking off (A9).**
- Cost: $1/$5 per MTok and no thinking tokens. That's roughly $0.005 per explanation, against about $0.04 on Sonnet
  5.5 and $0.08 or more on Opus 5.5. Both of those always think, and thinking is billed at output rates.
- Haiku 4.5 supports structured outputs, so guide and quiz generation work unchanged.
- With no thinking blocks, history is plain text. There are no preserved-thinking or cross-model replay rules to
  follow.
- An earlier answer chose Sonnet 5.5 for explain and Opus 5.5 for the other routes. A9 replaced it.

**Q5 — Refusal fallbacks.** **Answered on 2026-10-06: no fallbacks.**
- A refusal returns `ai_refused` with a hint to rephrase. `ai_call.refusal_category` records why, so the rate can be
  measured.
- Haiku 4.5 doesn't run the real-time cyber safeguards that the Opus and Sonnet 5.x models run, so security questions
  should be refused less often. Server-side fallback is documented only for the 5.x models anyway.

**Q6 — Thread length.** **Answered on 2026-10-06: at most 25 messages per thread.**
- That allows 12 questions. Asking a 13th returns 409 `thread_full`, and the user starts a new thread.
- A shorter history means less context resent on every turn (A9). History is never trimmed or compacted.

**Q7 — Where the API contract lives.** **Answered on 2026-10-06: `.orchestrate/api-contract.yaml`, tracked in git.**
- Why: the contract is the only thing that keeps the frontend and backend agents' halves matching, because the
  boundary hook stops each agent from seeing the other's code. A gitignored contract isn't versioned, isn't reviewed in
  pull requests, and disappears on a fresh clone.
- How:
  - `.gitignore` adds `!.orchestrate/api-contract.yaml`.
  - `AGENTS.md`, `.orchestrate/README.md` and `.claude/agents/orchestrator.md` note that this is the one tracked file
    in `.orchestrate/` (P0 step 3).
  - The frontend agent still writes the contract and the backend agent still implements it, so neither the boundary
    hook nor the agent paths change.
- Enforcement:
  - `frontend/src/types/api.ts` is generated from the contract with `openapi-typescript` (`bun run gen:api`).
  - Backend integration tests validate every response against the contract.
  - AC01 fails if the generated types are stale.
- Rejected:
  - `backend/openapi.yaml`: only the backend agent may write under `backend/`, so the frontend agent's draft would need
    copying over, leaving two copies that can drift.
  - Keeping it disposable: nothing versioned.

11. **H** In the Anthropic Console, create the API key in its own workspace with a low monthly spend limit (for
    example $5). Put it only in `backend/.env`, never in git (A3, A9).

### P1 — Auth (`feat/auth`)

1. **BE** Add a migration for `app_user`, `session` and `rate_limit`.
2. **BE** Add `POST /api/user` and `POST|GET|DELETE /api/session`:
   - Passwords hashed with argon2id.
   - Cookie `sid`: `HttpOnly`, `SameSite=Lax`, `Secure` in prod, 30-day sliding expiry.
   - The session token rotates on every login.
   - CSRF: reject any state-changing request whose `Origin` isn't `FRONTEND_URL`.
   - Login limited to 5/min per IP + email, then 429.
3. **BE** `requireSession` middleware sets `req.auth = { userId }`. Services receive it as an explicit argument, never
   from ambient context. Every tenant query is scoped through one ownership helper in `backend/src/service/`, so a
   later `orgId` changes one place (Q2).
4. **FE** Build the `/signup` and `/login` pages, log out, the redirect in `proxy.ts`, and the API client
   (`credentials: 'include'`, a 401 sends the user to `/login`).
5. **BE/FE/QA** Write a happy-path and a failure-path test for each endpoint, plus an e2e flow:
   sign up → log out → log in.

### P2 — Ask & explain (`feat/thread`)

1. **BE** Add a migration for `topic` (with seed), `thread`, `message` and `ai_call`.
2. **BE** Implement `TutorProvider` with the `anthropic` and `fake` implementations. The system prompt is a
   versioned constant in `backend/src/lib/tutor/prompt/` and is kept byte-stable so it caches.
3. **BE** Thread CRUD plus the SSE ask route. In order:
   1. Validate the question (1–20,000 characters).
   2. Check the budget.
   3. Take the per-user in-flight lock.
   4. Save the user message.
   5. Stream the answer.
   6. Save the assistant message and the `ai_call` row.
   7. If the client disconnects, abort and save what exists as `incomplete`.
4. **BE/FE** The user picks the topic when starting a thread (default `other`) and can change it with
   `PATCH /api/thread/:id`. There's no AI classification (A9).
5. **FE** Build `/thread` (list) and `/thread/[id]` (chat):
   - Streaming markdown with syntax-highlighted code and a copy button.
   - A "Thinking…" state and a Stop button.
   - Error toasts with a retry action.
   - An over-budget state, a thread-full state that offers a new thread, and a "cut off" note on answers that hit
     `max_tokens`.
6. **H** Run 10 representative questions with `AI_PROVIDER=anthropic`, which costs a few cents on Haiku 4.5. Record
   tokens and cost per explanation in `.orchestrate/`, then confirm or adjust the `AI_DAILY_TOKEN_BUDGET` default.

### P3 — Guidance (`feat/guide`)

1. **BE** Add a migration for `guide` and `guide_step`.
2. **BE** Add the routes:
   - `POST /api/thread/:id/guide`: structured output with 3–8 steps, each with a title, body, optional code and a hint.
   - `GET /api/guide/:id`.
   - `PATCH /api/guide/:id/step/:stepId`.
3. **FE** Add a "Guide me step by step" action in the thread. Build `/guide/[id]`: one focused step at a time,

### P4 — Quiz (`feat/quiz`)

2. **BE** Add the routes:

   - `POST /api/quiz/:id/attempt`: graded on the server.

### P5 — Progress (`feat/progress`)

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| AI cost runaway | Money (A9) | Haiku 4.5 with thinking off; `AI_PROVIDER=fake` by default; daily budget per user; low `max_tokens`; one generation in flight per user; 25-message threads; the `ai_call` ledger; `AI_ENABLED` kill switch; a Console spend limit as the hard backstop |
| Wrong explanations or wrong quiz answer keys | User trust | Zod checks on structure, an "AI can be wrong" notice, and per-item explanations on review so users can spot mistakes |
| Refusals on legitimate security questions | UX | Haiku 4.5 doesn't run the real-time cyber safeguards; a clear "rephrase" message; `ai_call.refusal_category` measures the rate. Server-side fallbacks are documented only for the 5.x models (Q5). |
| Prompt injection | Low: no tools, nothing secret in the prompt | Markdown with raw HTML disabled; nothing sensitive in the system prompt |
| Users paste secrets or PII into code | Privacy | Never log message content (pino redaction), a retention notice in the UI, soft delete |
| A proxy or CDN buffers SSE | Streaming breaks | `X-Accel-Buffering: no`, no compression on the SSE route, a heartbeat every 15 s, and an e2e test that checks delivery is incremental |
| Agents' knowledge of Next 16, Express 5, Tailwind v4, ESLint 10, Bun or the Claude API is out of date | Rework | Agents check current docs (context7, the `claude-api` skill) before using an API |
| Wrong Bun command: `bun test` runs Bun's own runner instead of Vitest, or a stray `npm install` writes a second lockfile | Misleading test results, dependency drift | The `AGENTS.md` Tooling rule, `bun run test` in every agent file, and `--frozen-lockfile` in CI |
| No password reset in the MVP | Users get locked out | Operator reset script; GitHub OAuth as fast-follow (Q3) |
| Missing repo tooling (root `package.json`, `dev-loop.js`) | Process friction | P0 adds `package.json`; phases can run without the driver (A6). Git is done (Q10). |
| `main` is unprotected until P0 step 10 enables branch protection | A direct or accidental push skips QA | The `git-workflow` approval gates until then; afterwards, a required pull request and CI check (Q12) |
| A public repo exposes everything committed | A leaked secret is public at once and stays in forks and caches | Secret-file hook, `.gitignore` for `.env*`, a history scan before going public (P0 step 2), and AC12's build grep |
| Seven phases is a lot of scope | Schedule | Each phase ships on its own. Stopping after P2 still leaves a usable product. |

## Rollout Order

1. P0 → P1 → P2 must run in order: everything depends on the foundation, auth and threads.
2. P3 (guidance) and P4 (quiz) both depend only on P2, so they can run on parallel branches.
3. P5 depends on P3 and P4. P6 comes last.
4. Each phase merges to `main` through a GitHub pull request, only after QA and CI pass and you approve.
5. There is no hosted release (Q11). "Done" means the full stack runs locally from `compose.yaml` and AC01–AC12 pass.

## Rollback

- **Code:** each phase is a single merge to `main`, so rolling back means reverting that merge commit.
- **Database:** migrations are additive and their `down` scripts are tested. A destructive change (a drop) never
  ships in the same release as the code that stops using it.
- **AI:** with `AI_ENABLED=false`, the AI routes return 503 `ai_unavailable` while history and progress keep working.
  `AI_PROVIDER=fake` stops all spend at once. Swapping to another non-thinking model is an `AI_MODEL` change; moving
  to a 5.x model is a code change (Q4).
- **Auth:** deleting the rows in `session` logs everyone out.
